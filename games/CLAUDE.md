# games/ — browser games at paddlesnitch.com/games

Paddling games that run in the browser. Like `firmware/`, this folder is **not a pnpm workspace package**: no `package.json`, no dependencies, no build step. Every file here is exactly what the browser runs, served as-is from S3.

The kayak game came from `baldur/games.snitchmedia.com` on 2026-10-17, with its history (`git log games/kayak`). This folder is its home now.

## The rules

- **Only native web platform features.** Canvas, WebGPU, Web Audio, Gamepad, Workers, DeviceMotion, Web Speech and so on are all fine. No libraries, no npm, no bundler, no transpiler: ES modules loaded straight from the server.
- **The one exception is WebAssembly.** A game may compile Rust (or C, Zig, …) to `.wasm` where it earns its place (heavy simulation, search, DSP). The source sits next to the committed `.wasm` with a one-line rebuild command, there's no `wasm-bindgen`/`wasm-pack` or generated glue, and it loads with `WebAssembly.instantiateStreaming`.
- **Sounds are generated in code** (`shared/audio.js`), not loaded from files.
- **Phone, keyboard and gamepad** all work.
- **Keep links relative** (`../shared/site.css`) so a game also works from `pnpm games` locally. The one absolute link is the favicon (`/favicon.ico`, the site's own).

## Commands

```sh
pnpm games        # serve games/ on http://localhost:8000 (open /kayak/); ES modules don't load over file://
pnpm games:site   # with `pnpm dev` running: the games under /games/ and the site behind them on one origin, http://localhost:8001/games/kayak/ (sign-in, leaderboards, live races)
node games/tests/live.mjs   # with both of those: two browsers sign up, race each other live, and check the leaderboard and sign-in gate
pnpm test:games   # node --test games/tests/*.test.js (Node's built-in runner); CI runs it on every PR and deploy
pnpm test:games:browsers   # plays each game in Chromium, WebKit and Firefox, desktop + phone, with features removed; add --gpu for real Chrome's GPU
node --test --test-name-pattern="false start" games/tests/*.test.js   # one test by name
```

`pnpm dev` (the Next app) doesn't serve the games; it does serve the `/games` index page.

## How it ships

Merging to `main` ships it. The CDK stack (`DeployGames` in `infra/lib/att-stack.ts`) uploads `games/` (minus `tests/` and `*.md`) to `games/` in the assets bucket, deletes files that were removed, and clears the CDN cache for `/games/*`. Browsers re-check after 5 minutes. A CloudFront Function (`infra/functions/games-router.js`) serves `index.html` for a folder URL, adds the trailing slash a bare folder URL lacks, and sends `/games/` to the `/games` page. `/game` redirects to `/games/kayak/`.

## Every browser, with a fallback for each feature

A game must run in current Chrome, Edge, Safari and Firefox, desktop and phone (iOS 15.4+, the first Safari with `<dialog>`), and anything optional must degrade, never throw. `tests/browsers.mjs` plays each game in all three engines with phone profiles and with features stripped; CI runs it on PRs that touch `games/` (the "games in browsers" check). Phones are emulated there, not real devices.

| Feature | Where it's missing | Fallback |
| --- | --- | --- |
| WebGPU | Firefox, iOS before 26, many Android phones; or it fails to start | WebGL 2 renderer (`kayak/render-gl.js`, loaded only then). `?webgl` forces it |
| WebGL 2 as well | very old browsers | the menu says so and disables the race buttons |
| `<dialog>` | iOS before 15.4 | a plain "too old" message (classic inline script) |
| Gamepad API | Firefox on Android | `navigator.getGamepads?.() ?? []` — never call it bare |
| Motion sensors | desktops; iOS without HTTPS or permission | touch play gets the balance assist |
| Speech | some browsers have none; iOS needs a first word in a tap | on-screen captions for every call; a silent word on the race button |
| Audio start | phones only count the end of a touch as a gesture | `shared/audio.js` unlocks on pointerup/touchend too, and resumes iOS's 'interrupted' state |
| Vibration, full screen, orientation lock | iOS | optional calls (`?.`, `.catch`) |
| Storage | private modes | every read and write in `try` |

The WebGL renderer must look the same as the WebGPU one: `shaders-gl.js` is a line-for-line port of `shaders.js` (keep them in step), with the same 4× MSAA and 24-bit depth, and WebGPU's 0..1 depth stretched to WebGL's -1..1. Without a GPU timer it sizes the resolution from frame times (`pacing.js`, tested): under ~45 fps it drops, a steady ~57+ it creeps back. A lost WebGL context (phones under memory pressure) reloads the page when it comes back.

## Layout

- `<game>/`: one folder per game, with `index.html` loading a `type="module"` entry script.
- `shared/`: what every game uses. Reach for these before writing new plumbing:
  - `site.css`: colour tokens (light/dark via `prefers-color-scheme`) and base styles for buttons, `<kbd>` and `<dialog>`.
  - `game.css`: game page layout (header bar, one `#field` canvas, a `.status` line). Set `--aspect` on `#field` to match the game's field units.
  - `audio.js`: Web Audio synth. `tone({ freq, to, duration, type, gain })` makes every sound. Also holds a mute setting kept in localStorage.
  - `input.js`: `Input` merges keyboard, pointer and Gamepad input into per-player `{ axis, target }`. Also `BUTTON` (standard gamepad indices), `poll()` (buttons newly pressed this frame) and `rumble()`.
  - `canvas.js`: `fitCanvas()` (high-DPI backing plus a transform so you draw in field units), `themeColors()` and `reducedMotion`.
  - `dialogs.js`: `openDialog()`, `gamepadDialogs()` (d-pad and A inside an open `<dialog>`) and `soundToggle()`.
  - `analytics.js`: counts a visit as a `pageview` (same endpoint, `/att/api/track`, and session id, `tt_sid`, as the site) and sends a game's own events: `window.gameMetrics.track(event, props)` queues them, and they go together in one `sendBeacon` when the page is hidden or left, or once a minute while some wait (20 a send at most); `beforeSend(fn)` adds a last event just before each send. Only on paddlesnitch.com: elsewhere the batches stay in `gameMetrics.sent` to look at. New event names must be on the site's allowlist (`METRIC_EVENTS` in `packages/ui`, `lead`'s), and every value must be lower-case words, numbers or a comma list of up to 60 characters, or the endpoint drops it. The game page loads this after its own module, so a game hooks in by `DOMContentLoaded`.
- `tests/`: Node tests for the pure simulation modules.

## Adding a game

1. Make `games/<slug>/index.html` and its modules.
2. In its `<head>`: `<link rel="icon" href="/favicon.ico">` and `<script src="../shared/analytics.js" defer></script>`.
3. Add it to `GAMES` in `apps/web/src/lib/games.ts` (title, one-line blurb, `href: '/games/<slug>/'`) so it shows on `/games`. `games.test.ts` fails if a folder isn't listed, or a game doesn't count its visits.
4. Put its pure logic in DOM-free modules and test them in `tests/<slug>.test.js`.

Every game covers the same baseline: keyboard, touch and gamepad controls; generated sound with the shared mute toggle; a "← Games" link (`href="../"`) in the header and inside the start menu's `.dialog-links` (a modal `<dialog>` makes the header unclickable).

## Game architecture

Split each game so the simulation can be tested without a browser:

- **Pure modules**: state and maths in fixed units, no DOM. A `step(state, dt, intents)` advances the game and returns event names; the UI turns those into sound and haptics, so the simulation never touches audio.
- **`main.js`**: wires the shared modules together. Input from `shared/input.js` (`poll()` once per animation frame). A rAF loop with a **fixed 1/120 s simulation step** (accumulator), so physics don't depend on refresh rate. Menus, pause and game over are native `<dialog>` elements driven by their `returnValue` in `close` handlers. Auto-pause on `visibilitychange`; respect `prefers-reduced-motion`.

### Kayak

A full-screen WebGPU view with its own renderer (`render.js`, `shaders.js`, `mat4.js`; WebGL 2 fallback in `render-gl.js`, `shaders-gl.js`, `pacing.js`) and procedurally built meshes (`meshes.js`, `world.js`). Its physics (`sim.js`), course geometry (`course.js`) and pack racing (`race.js`: the starter and false starts, rival AI, wash drafting, hull collisions, standings) are DOM-free and tested; a whole race can be simulated headlessly in Node.

**Features** (2026-10-30): things pointed out in the footage that aren't a whole building or a row of boats (a beach, a sign, a sculling club's racks, a ferry landing) are `features` in the course file, `{ style, at }` at a point on the bank, each drawn by its own function in `FEATURES` (`world.js`) in a frame facing the water from that point (`spot()`: y is up from the water's level, z out over the water, `ground()` for the land); trees keep `CLEAR` of them (drawn into the throwaway mesh, so the random draws don't change), and each feature takes its random touches from its own seed. A boat moored in a side channel (the trip boat in Piper's north channel) is a `moorings` entry with `at` and `dir`: placed there by `berth()` in `world.js`, solid (`mooringBoxes`), narrowing only the route near it, not the river line's water. Boats moored along a bank are nudged apart where they'd overlap on the inside of a bend (`spaceOut` in `course-file.ts`; `kayak-scenery.test.js` checks no two lie in each other). Landmarks added from the review: `victorian` (the white turreted house at 1.8 km), `island-bar` (Piper's Island). Features: `boat-shed`, `ivy-boathouse`, `quay`, `truss`. The distant hills round a real river are low wooded downs (`HILLS`), and railway masts stand 11 m so they show over the riverside trees. The 0.1-0.4 km review frames were taken up Fry's Island's back channel (40-80 m off the river line): boats seen there are moored at their own points. Woods are planted out to `WOOD_REACH` (140 m) and trees beyond `FAR_TREE` (70 m) get one ball of crown: about 21k triangles saved, the random draws kept (trees out of reach are drawn into the throwaway mesh). A duck off the racing line that drifts onto dry land or into a moored boat is put back on the nearest water; swans aren't touched (any change to how swans move shifts where they meet the pack: measured, a swan version gave a paddler a second swim). **The land beside a side channel far off the river line** (Fry's Island's back channel, 75-100 m out, on the Hasler 7-9 route) is drawn finely, rows every 2.5 m round its water (`FAR_WATER`), and its height slopes down to the nearest mapped shore at any distance (`ground()`). Real rivers come from course files (`kayak/courses/<id>.json`, made by `apps/web/scripts/courses`; see `docs/features/game-courses-from-video.md`): `courseFromFile`/`loadCourse` in `course.js`, fetched when first picked, and `world.js` draws their `scenery` (real buildings, styled bridges, moorings, woods, railway, banks by cover) instead of the made-up props. They're true size, so they have a `speedup` (boats move that many times their speed through the world; `sim.js` `move()`) as well as a `warp`, and the HUD's distance is `× warp / speedup`. Course files are ODbL (derived from OpenStreetMap): keep the menu's credit line. They also carry `places` (landmarks named on screen as you pass), `walls` (quays and revetments), `birds` (where swans crowd), `water` (the mapped water's outlines: `world.js` shapes the land from them, so islands and side channels show) and buildings with a `style` drawn as bespoke models (`LANDMARKS` in `world.js`: the Reading rowing and canoe clubs, and the spiral-stair boathouse, grey boathouse and riverside villa the owner pointed out; an unnamed building gets a style from a `landmark` observation at a point beside it), `posts` (standing in the water, solid: in `course.shore`), `anglers` (`anglers.js`, pure, tested: on the bank with a line to a float; paddle across its low end and it snags you once, the `line` event, a quarter of your speed left; rivals pass on the float's side; placed with no randomness so live races agree), tatty moorings (`kind: 'tatty'`), and get a cloudy sky (`skyTop.w` is cloud cover; 0 on the made-up courses). A course file with a `route` (the Time Trial Loop) races on that line instead of the river line: `courseFromFile` returns the route as the course and the river line as `scenery.river`, which everything in the file is placed along; moored boats narrow the route wherever they lie, and `shared` marks water the route uses both ways (the AI keeps right there). Where a file maps its `water`, boats meet the real banks, islands and moored boats (`course.shore`: `water.js` `shoreOf`, `sim.js` `bounceOffShore` in place of `bounceOffBank`), so a boat isn't snapped sideways where the open-water edge jumps at an island's end, and other channels are really open (heading into a bank, a boat turns along it at `BANK_TURN`, never in one frame; the water's tree reflections come from `riverView`, eased for the same jumps); the AI still steers by the route's edges. A route course can have `gates` (race.js: reach one's distance along outside its own water and you've missed it, `missed` event and the red `#missed` message, no finish until you go back for it), `cues` (an arrow and a line under the clock as you come up to a turn: `#cue`), `marks` (turning buoys in `world.js`, yellow on both maps) and flocks `at` a point off the line (`birds.js` `away`: kept to the real water). The close-up map draws a real river's water (islands as holes) and the racing line. Routes are rebuilt with `pnpm --filter web course:route <id>` (docs/features/game-courses-from-video.md). Lining up happens at true speed: `race.js` switches every boat to the course's `speedup` at the horn (or when it's let go), and the pack AI scales its distances (kick, sprint off the line, station-keeping on a wash, look-ahead) by it. `createRace(..., { format: 'interval' })` is a time trial: boats wait in two columns below the line and go 30 s apart (as shown), each timed from crossing the start line; `elapsed()`/`projected()` give a racer's time so far and what they're on track for. Swans and ducks (`birds.js`) are on every course: paddle into a swan and you capsize, ducks fly off; rivals steer round swans. Other boats use the river too (`traffic.js`, pure, tested), the same on every course: single scullers, kayakers out paddling (`kayakerMesh`, the paddle swung in `main.js`), eights, pleasure cruisers and motorboats, real sizes and speeds (motorboats at the Thames's 8 km/h). They keep to their right of the river's main channel (`scenery.river` on a course with a route, so never the Loop's side channel at St Mary's) and don't react to anyone, so a live race's copies see the same boats. Each is timed to meet the pack once at a random moment (gaps average 120 s and vary a lot: some races are empty; owner 2026-10-31: busier than the 150 s it was. Measured over 16 seeded races on each real course against main: traffic hits 9 against 12, swims 48 against 49; on the narrow made-up test river a few more eight hits, so the race tests' traffic limits grew a little) and is only on the water for a while either side of it. Scullers, cruisers and motorboats only ever come towards the race; an eight now and then comes up from behind, but only where the river is 18 m wide or more, from the bottom of the river: the cox shouts (`behind-left`/`-right` events: speech, a message and the red `#behind` arrow) about 30 m off. Hitting a hull or oars capsizes you (once per boat); motorboats and eights leave a wash on the two arms of their V that rocks you (`trafficWash`, added to the kayak wash). The rivals pass by the rule of the river (oncoming boats on their left, an eight from behind on their right: `trafficNear`'s `pass`), looking about 12 s ahead; on the narrow made-up river one still gets clipped about one race in seven. The boats are `meshes.js` scullerMesh/eightMesh/cruiserMesh/motorboatMesh, with oars (`oarMesh`, `ROWLOCKS`) swung in `main.js`; they get wakes in the water shader's spare boat slots, grey marks on both maps, and a motorboat's engine is a low rumble as it passes.

**The courses (owner's choice, 2026-10-30): one river, different routes.** Every course is on the real Thames at Reading, so the scenery is always the same. `MODES` in `main.js` lists them: **Time Trial Loop** (5.3 km, round St Mary's and Fry's islands), **Hasler Div 7-9** (7.9 km: up the main channel and round Appletree Eyot's top, down its back channel, past the club, down the right of Fry's Island, round its end, up its back channel, and home), **Hasler Div 1-6** (12.6 km: up to Mapledurham, land on the beach, run the bank path, put in behind the island, down round Fry's Island and home; the Division 3 pack, `DIVISION_3` in `race.js`) and **Practice** (1 km up from the club, on your own). Both Hasler courses keep right of Piper's Island both ways (the south arch going down, the narrow north channel going up), gated. The menu picks **Race** (everyone off together, `format: 'mass'`) or **Time trial** (interval starts), remembered in `localStorage`; your best is kept per course and format, and a leaderboard per course. Live races are always mass starts. The made-up Division 9 river (`raceRiver`) and practice river stay in `course.js` for the physics tests only. Each course file is `kayak/courses/reading.json`'s world (`world: 'reading'`) plus its own `route`, `places`, `birds`, `gates`, `cues` and `marks`, written by `course:route` from `apps/web/scripts/courses/data/<id>/course.json` (`kayak-courses.test.js` checks the scenery is the same in every file). `main.js` builds the river mesh once per world (`buildWorld(course, seed, 'river')`) and each course's buoys, gantries and boards on their own (`'course'`); building the whole world per course would hold four copies of about 385k triangles on a phone. **A portage** (`route.portages`, `{ from, to }` along the route: the stretch between runs over land) is yours to do, and the rivals do the same (owner's choice, 2026-10-30; `PORTAGE` and `carry()` in `race.js`): come into the beach slowly (within 12 m, under 1.5 m/s) and press both sides together to jump out (a left and a right tap within 0.2 s: both arrow keys, both thumbs, or LT and RT; a stroke can't come that close to the last, so paddling never triggers it). Come in quicker and you run aground within 3 m: stuck 3 s (as shown). Then run: every tap is a stride, any side; 2 a second is a 2.5 m/s jog, each tap a second more is 1 m/s faster (to 4.2); quicker than the jog spends sprint stamina, which only comes back at a jog or slower (it used to refill between strides, so an empty bar still ran flat out). Carried, there's no physics, hazards, wash or gates (the boat on your shoulder, your eye at standing height). At the put-in (a little beach, `landing`, 10 m up from the sandbag wall, which blocked the old one) press both sides again to get in: 3 s, then afloat from a standstill with a wobble, and a stroke in the first 4 s rocks it harder (`rushed`). Rivals coast in from 70 m, back-paddle if still quick, jump once slow, stride at a pace set by their power (easing to a jog when tired), react 1.5-3 s at the beach and put-in, and sit still until settled. Paddle past without landing and it's a miss like a gate's, cleared when you've run it. The run follows a mapped footpath (`paths` in the world, from a `path` observation): a gravel strip, and trees and scrub keep off it (drawn into a throwaway mesh, so the random draws and the rest of the world don't change). **Practice** (the menu's practice page): drills in `drills.js` (pure, tested), each on one of the courses with no swans or traffic: **Starts** (four rivals and the starter; your reaction to the horn and the first 100 m, place at 100 m, false starts), **Wash hanging** (a pacer under way at a steady 83 a minute on Hasler 7-9: seconds on its wash, the longest spell, metres back when off), **The portage** (150 m below the beach: splits for the landing, the run, getting in and 100 m away), and the free 1 km paddle. Each drill's best is kept in `localStorage` (`snitchmedia:kayak:drill:<kind>`); drills don't go on leaderboards. **Lessons:** a mass start on a course that finishes where it starts must locate the boats on the first stretch (`locate` with a hint), or they're placed on the finish pass and "finish" at the horn (the Loop was only ever a time trial, so it never showed). A course passing a crowd of swans gave rivals streaks of five swims (back in, straight into the next swan): `SWAN_GRACE` (3 s) after a swan capsize. A flock in a narrow channel the route goes up (Piper's north channel) needs fewer swans than one beside the line. Simulating a mass start in Node needs the player lined up (`lineUp` in the tests) or the starter waits for ever and the race clock never runs. The browser check (`tests/browsers.mjs`, CI job "games in browsers", 30 minutes) is slow in CI's Chromium, which draws the full river in software (4 to 6 minutes a case since practice moved onto it): add new cases in WebKit, which takes under a minute.

Outings get busier traffic (`BUSY`): the cruise a boat about every 35 s along its own route (`createTraffic`'s `route`), the launch boats up and down the whole river already under way (`ambient`, some 20 on the water at once), so traffic meshes hold 24 each. Boats: `tripBoatMesh` (21 m, glazed saloon, a railed foredeck) and `launchMesh` (open well, cushions, canopy, wheel). The HUD drops the race readouts (`#hud.outing`) for the `#outingBar`.

**Rowing** (owner 2026-10-31: a single scull, one way to row; Reading Rowing Club across the river is open now, its red boards gone). `scull.js` (pure, tested): the same boat object as a kayak with `hull: SCULL`, so `race.js` races it (it steps a scull with `stepScull` instead of `sim.js` `step`). **Each oar is its own:** ← and → (a thumb each side, LT and RT) catch it, it drives for 0.7 s, and it can't catch again until it's been round the recovery (about 40 a minute at most). Both within 0.2 s are one stroke and **finish together**, so the oar in first pulls the longer stroke and the bow comes round from it: that's how you steer (a tenth of a second early turns about 3° a stroke); one oar alone spins the boat. Alternating them is slower than both together, burns the stamina and builds no rhythm. About 11 km/h at 22, 13 at 30, 16 flat out at 38. **Balance** is gentler than the kayak's: a lone oar jolts the boat at its catch, the wash and chop rock it, the blades on the water steady it, and past `crabAt` you **catch a crab** (the boat nearly stops, 1.4 s to get going); only a knock (a swan, a boat) tips you in. Three sculls on the boathouse rack (`SCULLS`: trainer, club, fine), and a colour from a set; both kept on the device (`snitchmedia:kayak:row`), not the account (the account's kit is the kayak's: adding them there is `lead`'s schema). **The view:** you sit facing the stern (the camera looks back down the boat, wider than a kayak's, `ROW_WIDE`), your legs, arms and both oars drawn from `scullPose` (`placeMyScull` in `main.js`; not your body: the camera's in your head), the hull from `scullHullMesh` (riggers, slide, stretcher, shoes, the coach); **the stroke coach** on the stretcher shows rate, split /500, time and metres in an HTML panel over its screen (`placeCoach`); **hold ↑** (Y on a pad, the Look button on a phone) to turn round over your shoulder and see where you're going. Rowing in an all-in-one: your top's colour, bare arms (`suitOf`). **Modes** (`ROW_MODES`): a practice row (1 km up from the club) and the Head of the River (a head race is a time trial: the Loop, scullers 30 s apart); the rivals are the kayak AI drawn as the river's sculls with their oars swung (`rowingRivals`). No leaderboard for rowing yet (a local best each, on the clubhouse's honours board). **The erg room** (`erg.js`, pure, tested): a 500 m on your erg, either side a stroke (both together count once), power from the strokes eased as a monitor does, pace from watts = 2.8 / (s/m)³ (about 2:28 at 20, 2:03 at 30), the rower on the next erg holding 2:08, your best kept on the device; the erg's numbers sit over its monitor (`#ergMon`). The ergs (`ergMesh`, seat, handle) and the rowers on them (`rowerParts`: body leaning, legs bent by `bend`, arms to the handle) are placed only while you're in the room: a mesh stands in one place a frame. **The mural** on its wall is drawn in flat shapes after the one at Reading Rowing Club (`mural` in `club.js`): the sky, trees, a crowd with parasols, a dog, a quad and a pair, a sculler big as life on the left, and the two huge faces on the right. **Lesson:** an element with a `display` rule in the CSS ignores `hidden`: give it `[hidden] { display: none }` (the coach stayed up while looking back).

**Analytics** (owner 2026-10-31: how long people play, what they pick, what they do; `metrics.js`, pure, tested): `game_play` when a race, outing or drill ends (mode, course, how it ended, seconds, place, swims, from the walk or the menu; on an outing also km, bumps and rowers or kayakers knocked in, to tell exploring from mischief), `game_kit` when play starts and the paddler has changed (body type, hair, hat, facial hair, buoyancy aid, sunglasses, sleeves, boat, paddle, shape; never colours or skin tone) and `game_session` before each send (seconds in view since the last send, so sum per session for its length; plays; the walk's places; the controls used; the renderer). Nothing about who: the random per-tab session id only. The browser check's outing cases confirm the events are made. **The server keeps only what its rules allow** (`GAME_EVENT_PROPS` in `packages/ui/src/metrics-events.ts`, `lead`'s, #757): a new choice in the game (a hair style, a course, an outing) is dropped from the numbers until it's added there, and each event is at most 10 props (`game_play` is at 10), so tell `lead` before adding an option or a key. `apps/web/src/tests/game-events.test.ts` runs every event the game can make through those rules and fails on anything they'd drop.

**Accounts, leaderboards and live races** ([`docs/features/game-accounts-leaderboard-live.md`](../docs/features/game-accounts-leaderboard-live.md)). The game calls the site's tRPC API (`games.*` in `packages/api`, store in `packages/core/src/games.ts`) with plain `fetch` (`kayak/account.js`): it's served from the same origin, so the sign-in cookie comes along. Practice is open to everyone; the races, the leaderboards and live races need an account (signed out, a race button goes to `/signin?next=/games/kayak/`). Served on its own (`pnpm games`, the browser tests) there's no API, so nothing is gated. A finished race posts its time (as shown) to the course's leaderboard; the menu shows the top five. Live races ("Race friends"): the dialog asks first whether you're making a race (pick the course) or joining one (just the code: the course is the maker's; a `#race=` link goes straight there); one player makes a race and shares `#race=CODE`; every phone holds one WebSocket to our relay (API Gateway + a Lambda, `infra/lambdas/game-relay/`, state in S3), which passes each message on to the others: no direct phone-to-phone connections (those failed on real home networks). `games.live.create`/`.join`/`.ticket` hand out a one-use ticket to connect with (`kayak/live.js`; it reconnects with a fresh one if the connection drops). Boat states go 10 times a second; the lobby shows the round trip to each player. The other players are racers with `remote: true` in `race.js`, drawn 200 ms behind their sender between received states (`kayak/net.js`, pure, tested); the host's game runs the starter and the others follow its calls (`applyCall`). Locally `pnpm games:site` runs the same relay code at `ws://localhost:8001/live`.

Race courses have a `warp`: the HUD shows distances and times 4× longer than what is actually paddled, so a 6 km race (shown as about 28 minutes) plays in about 7, while speeds and stroke rates stay real. Courses vary in width along the way (`widthAt`), and moored narrowboats count as bank. Where a boat is along the course is the nearest point on the line (`locate`), so on a bend tighter than the water is wide (the loop's turns round the island ends) a boat out on the inside would be nearer another part of the line and jump along it; `createCourse` brings the open water in on the inside of such bends until every point of it maps to its own part of the line (`withinReach`; tested by paddling every course at five lines across the water, `tests/kayak-course.test.js`). The HUD's course map (`map.js`, pure; drawn as SVG by `main.js`) shows the race's part of the course north up, in a box the course's shape (wide for an east-west course, tall for a north-south one), start in green, finish in white, a dot per boat (yellow computer rivals, blue live players) and a red arrow for you. Beside it, top left, a round close-up (`closeUp`/`follow` in `map.js`) shows the open water about 100 m across, turned each frame so your heading is up and you sit a little below the middle: the water is drawn once per race as one small four-sided shape per few samples, all wound the same way so it stays filled where the river passes itself, and the SVG group is moved and turned under you. It hides while the phone controls help is showing. Speed comes from how quickly you tap (owner's choice, 2026-10-25): there's no sprint button and no beat to follow. Up to `steadyBeat()` (90 a minute) paddling is free and refills the sprint bar (stamina), at any slower rate too; quicker than that is a sprint, read from the average of the last two gaps (one hurried tap isn't one): each stroke pulls up to 20% harder (full at about 110 a minute, `sprintBeat`) and spends stamina, more the quicker. Out of stamina, a beat quicker than 90 pulls no harder than 90. A wash refills it several times faster, up to full. Rhythm (how even your own beat is: no metronome, the rhythm bar shows it) still matters, but an uneven beat costs at most about a fifth (`rhythmBase` 0.8; 0.85 stable, 0.75 racing), and holding it builds `flow` (up to +6% power over 20 s). Back strokes (owner's choice, 2026-10-25): hold ↓ and press ←/→, gamepad LB/RB (LT/RT forward), or swipe a thumb down on a phone (a touch becomes a forward stroke when it lifts, slides sideways or stays down 150 ms, so a swipe can be told from a tap). Each pushes the boat back (braking first) up to 1.5 m/s astern and swings the bow towards its side, `backYaw` 4 times a forward stroke's swing, so alternating backs you out straight and one side turns you on the spot; going backwards the rudder works the other way round. No stamina, not in the stroke rate, and it breaks your beat. Getting nowhere for 3 s mid-race shows how, twice a race at most (`stuckHint`). Why: just past the end of St Mary's Island a narrow slot between an islet's tip and the bank turns a paddler round, and then the rudder can't bite and forward strokes drive into the islet: a simulated human-like paddler stalled there (and at the end of Fry's Island) 25 times in 24 runs of the Loop without back strokes, none with them. The rivals sprint the same way, by paddling quicker: about 100 a minute to catch a wash or off the start, 98 for the line. Cheaper sprints (96) had them chasing every wash across the river, hitting more swans and getting clipped by eights: measure capsizes and traffic hits over 12-16 seeded races against main before changing these (one seed proves nothing; main itself capsizes a rival on 5 of 12 Reading seeds). The pack is tuned (`RACE_PACE`, `RIVAL_POWER` in `race.js`) so a person, rarely perfectly on the beat, can race it: the Division 9 winner takes about 31 minutes; hull types (`HULLS` in `sim.js`) trade speed for stability. Session form (stronger, fitter, steadier on the beat after each race) lives in `sessionStorage`. On phones, turning the phone shifts your weight (`controls.js`, DeviceMotion; iOS only allows it over HTTPS, and without it touch play gets a balance assist), and pushing one side of it away from you steers (the gyroscope's turn about the screen's upright axis: right side forward goes left; `twistRate`/`stepTwist`/`twistRudder`, tested; 3 degrees dead, full rudder at 20, re-centres over 30 s; sliding a finger still works). Every browser gives `rotationRate.alpha` about the phone's x axis, `beta` about y and `gamma` about z; the spec's old wording (alpha about z) is wrong. The first version followed that wording and read the wrong axis: in landscape it steered when the phone tipped back. Its test made the same mistake, so the tests are written against the phone's physical axes. The renderer lowers its resolution when the GPU falls behind. Open `kayak/#debug` to expose `window.kayak` (race, boat, location, course, state, GPU stats) for scripted playtests.

## The site side (`/games`)

Moved from the root `CLAUDE.md`.

Browser paddling games live in **`games/`** at the repo root. Like `firmware/` it is not a pnpm package: plain HTML/JS, no build, no dependencies — see the sections above for its rules and how to add a game. Kayak came from `baldur/games.snitchmedia.com` with its history (2026-10-17); this repo is its home now.

- **Index page:** `/games` (Next, `src/app/games/page.tsx`) lists `GAMES` from `src/lib/games.ts`; `games.test.ts` fails if a `games/<slug>/` folder isn't listed or doesn't load `../shared/analytics.js`. `/game` 307s to `/games/kayak/` (next.config).
- **Serving:** CloudFront `/games/*` → the assets bucket at key prefix `games/` (separate from OpenNext's `_assets/`; no lifecycle rule matches it). A CloudFront Function (`infra/functions/games-router.js`, tested in `src/tests/games-router.test.ts`) serves `index.html` for folder URLs, adds the slash a bare folder URL lacks (games import `../shared/` relatively), and sends `/games/` to `/games`.
- **Shipping:** merging to `main`. The `DeployGames` BucketDeployment uploads `games/` (minus `tests/`, `*.md`) with `max-age=300`, prunes removed files and invalidates `/games/*`. CI runs `pnpm test:games` (`node --test`) in checks + deploy, and on PRs touching `games/` the "games in browsers" check (`pnpm test:games:browsers`: Chromium/WebKit/Firefox, desktop + phone, features stripped).
- **Every browser:** kayak draws with WebGPU, else WebGL 2 (`?webgl` forces it); each optional feature has a fallback — table in `games/CLAUDE.md`.
- **Visits:** `games/shared/analytics.js` sends one `pageview` to `/att/api/track` (same session id as the site), so games show in "pageviews by path".
- **Locally:** `pnpm games` serves `games/` on :8000; `pnpm dev` serves the `/games` page but not the games.
- **Lesson (2026-10-25): finding what the owner points at.** Given a GPS point, find each recording's fixes within ~40 m in `.cache/courses/<rec>/track.json` and pull a flat view from the 360 at that moment, turned towards the point (ffmpeg `v360`, as `frames.ts`; narrow `h_fov` to zoom). Then compare from the water: `#debug`, put `window.kayak.boat` at a point facing it, screenshot (headless Chromium with SwiftShader works). Check a new AI-avoidance test fails with the avoidance switched off: the first anglers test passed either way, because the Reading line never went near the lines.
- **Real-river courses from 360 video** ([`game-courses-from-video.md`](../docs/features/game-courses-from-video.md)): GoPro telemetry (`@paddlesnitch/timing/gpmf`, GPS9 + GPS5) → OSM river line + widths → frames every 50 m per pass → geo-referenced observations (`apps/web/scripts/courses/data/<id>/observations.json`) → `games/kayak/courses/<id>.json` (ODbL: derived from OSM; credited in the menu). Steps: `pnpm --filter web course:ingest|course:river|course:frames|course:build|course:compare`; working files in `apps/web/.cache/courses/`. The river: **Reading Thames** (Christchurch Bridge → Mapledurham, `courses/reading.json`, no longer raced on its own); the courses on it: the **Time Trial Loop**, **Hasler Div 7-9**, **Hasler Div 1-6** (with a portage) and **Practice**, each a `route` in its `course.json` built from legs along the river line, through points and over a portage, drawn true size with `speedup: 4` (boats move 4× their speed) and `warp: 4` (times shown 4×), so the HUD shows true distances and times. Set `cameraYaw` per recording: the Reading camera faced forward from the back deck (180).
- **Accounts, leaderboards and live races** ([`game-accounts-leaderboard-live.md`](../docs/features/game-accounts-leaderboard-live.md)): the game calls `games.*` on the tRPC API (`packages/api/src/routers/games.ts`, store `@paddlesnitch/core/games`): a leaderboard per course (`games/kayak/leaderboard/<course>.json` in the data bucket, best per player, names as "First L.", plausibility-checked times) and live races (`games/live/<code>/`; expired after a day by a lifecycle rule). Every live race goes through the **game relay**: an API Gateway WebSocket API (`GameRelayApi`, stage `live`, throttled to 500 msg/s) and one Lambda (`infra/lambdas/game-relay/`, plain JS, state in S3 only); the site's API hands out one-use tickets to connect (`RELAY_URL` on the server tells the game where). No direct phone-to-phone connections: those failed on real home networks. Paid per message (a few cents a race, nothing idle). Races need an account; practice doesn't. Locally, `pnpm games:site` puts the games and `pnpm dev` on one origin (:8001) and runs the same relay code at `/live`.
